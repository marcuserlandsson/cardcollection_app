## Rulings

**Ruling: merge Tasks 2, 3 and 4 into a single implementer dispatch.** — The three are mutually circular: `lib/types.ts` needs `GameId` from `lib/games/types.ts`; `lib/games/digimon.ts` calls `validateDeck` from T4; `validate-deck.test.ts` and the T4 helpers build `Card` objects carrying T2's new fields. No ordering of the three reaches a green suite or a clean `tsc` on its own, so committing them separately would mean knowingly committing broken intermediate states. The plan itself half-anticipated this ("Task 2 and Task 3 may be committed together"), which is the tell that the task boundary was drawn wrong. — **Cost if wrong:** one larger review surface (3 files + 6 fixture files) instead of three small ones; if the reviewer finds a defect it is harder to attribute to a single task. Mitigated by keeping the plan's three separate commits inside the one dispatch.

**Ruling: accept the type-only import cycle between `lib/types.ts` and `lib/games/types.ts`.** — Both directions are `import type`, so TypeScript erases them and no runtime cycle exists; `lib/types.ts` has no runtime exports at all. `eslint-config-next` does not enable `import/no-cycle`, so it will not be flagged. The alternative — moving `GameId` into `lib/types.ts` — would split the registry's type surface across two files for no benefit. — **Cost if wrong:** if a future bundler or lint rule objects, `GameId` moves to `lib/types.ts` and `lib/games/types.ts` re-exports it; a two-line change.

**Ruling: Task 1's implementer writes the migration file only; applying it is a human step.** — There is no `supabase/config.toml` and no linked CLI, and Postgres DDL cannot be executed through the Supabase REST API, so the migration must be pasted into the dashboard SQL editor by the account holder. Applying it also mutates live production data holding a real collection — an outward-facing, hard-to-reverse side effect that SDD says to ask about rather than assume. The implementer's deliverable is therefore the committed SQL plus the verification queries; steps 2–4 of the task (apply, verify backfill, verify trigger) are handed to the human partner. — **Cost if wrong:** none to the code; the risk is schedule, since Tasks 7–10 cannot be verified against real data until the migration lands. Tasks 2–6 are unaffected because they touch no database.

**Ruling: Task 11's UI walkthrough is executed by the human partner, not a subagent.** — Steps 2 and 3 require driving a browser against a dev server and comparing against remembered pre-change behaviour. I will run the automated half (`npm test`, `tsc --noEmit`, `lint`, `build`) and hand over the manual checklist. — **Cost if wrong:** a visual regression could reach the Cyberpunk phase unnoticed; mitigated by the checklist being explicit about what to compare.
